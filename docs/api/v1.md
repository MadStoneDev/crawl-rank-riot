# RankRiot Jobs API — v1

The public, API-key-authenticated interface to RankRiot's crawler. A **job** is
a scan: you create one, poll it, then read its scored report and issues. It runs
the exact same pipeline as the RankRiot app, so results match the dashboard.

This document is the contract Vanward builds against. Recorded example responses
live next to it in [`samples/`](./samples/) and are generated from the real
scoring + serializer code (`crawl-rank-riot/src/scripts/generate-v1-samples.ts`).

- **Base URL:** `https://<crawler-host>/api/v1`
- **Status:** the surface and schemas below are implemented. Provisioning of API
  keys is operator-side until the key-management UI ships (see
  [Provisioning](#provisioning)); the backing tables are created by
  `crawl-rank-riot/migrations/2026-10-22_0001_v1_jobs_api.sql`, which a human
  applies.

---

## Versioning

Every response carries two versions:

```json
{ "api_version": "v1", "schema_version": "1.0.0", "data": { ... } }
```

- `api_version` — the URL/surface version. Only changes for a breaking redesign.
- `schema_version` — semver of the response bodies. Minor bumps are additive and
  backwards-compatible (new fields); a major bump is a breaking shape change.

Assert `api_version === "v1"` and that `schema_version` is a major you support.

## Authentication

Send your key in **either** header:

```
Authorization: Bearer rrk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
X-API-Key: rrk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Keys look like `rrk_<env>_<random>`. Only a SHA-256 hash is stored server-side,
so a key is shown **once** at creation — store it securely; it cannot be
recovered. A key belongs to a RankRiot user and can only act on that user's
projects.

### Scopes

| Scope | Grants |
|-------|--------|
| `jobs:read`  | list/read jobs, reports, issues, usage |
| `jobs:write` | create and cancel jobs |

A request missing the required scope gets `403 insufficient_scope`.

### Public endpoints (no key)

- `GET /api/v1/health` — liveness.
- `GET /api/v1/meta` — versions, scopes and the endpoint list, for discovery.

## Rate limits & usage

- **Per-key rate limit:** each key has its own requests-per-minute limit
  (default 60). Over it → `429 rate_limited`. `RateLimit-*` response headers
  report the window.
- **Monthly job quota:** a key may have an optional monthly cap on *jobs
  created*. Over it, `POST /jobs` returns `429 quota_exceeded`.
- **Metering:** every authenticated request and every created job is counted per
  key, per UTC day. `GET /api/v1/usage` returns month-to-date totals and the
  remaining quota. See [`samples/usage.json`](./samples/usage.json).

## Issue categories, severity & the speed tag

Each issue and each report deduction is classified consistently, and the API
exposes it in a display-ready form so Vanward needs no mapping of its own.

- **`category`** — one of `technical`, `content`, `media`, `aeo`. This is
  RankRiot's single source of truth for grouping (the crawler's score category).
  `category_label` is the display label: `Technical` / `Content` / `Media` /
  `AEO`.
- **`severity`** — `critical` | `high` | `medium` | `low`, taken from the
  issue's stored severity (the single source of truth; not re-derived).
- **`is_speed`** — a cross-category **speed** tag. Load performance spans two
  categories (page performance is `technical`, image performance is `media`), so
  there is no single "speed" category; `is_speed: true` marks the issues that
  are about load performance (`slow_page`, `slow_server_response`,
  `large_page_size`, `oversized_images`, `non_modern_image_format`,
  `missing_image_dimensions`). Use it to offer a "Speed" view that draws from
  both categories.

A report's `categories[]` gives the four category health **scores** (0–100) and
a separate **pass_rate** (0–100) — two distinct axes; display them separately.

## Jobs

### Create a job — `POST /api/v1/jobs`

Scope: `jobs:write`.

```json
{
  "type": "seo",
  "project_id": "9c8b7a65-4321-4a1b-8c7d-6e5f4a3b2c1d",
  "options": { "maxPages": 500, "maxDepth": 5 }
}
```

- `type` — `"seo"` (default, full crawl) or `"audit"` (shallow).
- `project_id` — a project owned by the key's user. **Required.**
- `options` — optional crawl overrides; clamped server-side to safe ranges
  (`maxPages` 1–100000 for seo / 1–500 for audit, `maxDepth` 1–10 / 1–5,
  `concurrentRequests` 1–10, `timeout`). Unknown fields are ignored.

Returns `202 Accepted` with the job (status `running`). The scan runs
asynchronously; poll the job. See [`samples/job.json`](./samples/job.json).

Errors: `400 validation_error` (no project_id), `403 forbidden` (not your
project), `404 project_not_found`, `409 scan_in_progress` (one already running
for that project), `429 quota_exceeded`.

### Get a job — `GET /api/v1/jobs/:id`

Scope: `jobs:read`. Returns the job with its current `status` and `stats`.

```json
{
  "object": "job",
  "id": "3f1c9a2e-…",
  "type": "seo",
  "status": "completed",
  "project_id": "9c8b7a65-…",
  "created_at": "2026-10-22T09:00:00.000Z",
  "started_at": "2026-10-22T09:00:01.000Z",
  "completed_at": "2026-10-22T09:03:12.000Z",
  "stats": { "pages_scanned": 3, "links_scanned": 48, "issues_found": 5 },
  "failure_reason": null,
  "links": {
    "self": "/api/v1/jobs/3f1c9a2e-…",
    "report": "/api/v1/jobs/3f1c9a2e-…/report",
    "issues": "/api/v1/jobs/3f1c9a2e-…/issues"
  }
}
```

**Status lifecycle:** `queued` → `running` → `completed` | `failed` |
`cancelled`. Poll `GET /jobs/:id` until the status is terminal (a few seconds
between polls is plenty).

### List jobs — `GET /api/v1/jobs`

Scope: `jobs:read`. Query: `limit` (1–100, default 25), `offset`. Returns the
calling key's jobs, most recent first.

### Report — `GET /api/v1/jobs/:id/report`

Scope: `jobs:read`. The scored report for a completed job. `404 report_not_ready`
while the scan is still running. See [`samples/report.json`](./samples/report.json).

### Issues — `GET /api/v1/jobs/:id/issues`

Scope: `jobs:read`. Query: `limit` (1–200, default 50), `offset`. Open issues
for the job, each with `category`, `category_label`, `severity`, `is_speed`,
`page_url` (null for site-level issues) and `description`. See
[`samples/issues.json`](./samples/issues.json).

```json
{ "object": "list", "job_id": "…", "items": [ … ],
  "page": { "limit": 50, "offset": 0, "total": 5, "has_more": false } }
```

### Cancel — `POST /api/v1/jobs/:id/cancel`

Scope: `jobs:write`. Requests cancellation of a running job and returns the job
(status `cancelled`). No-op if already finished.

## Usage — `GET /api/v1/usage`

Scope: `jobs:read`. Month-to-date usage for the calling key.

```json
{ "object": "usage", "period": "month", "period_start": "2026-10-01",
  "requests": 1284, "jobs_created": 37, "quota": 500, "quota_remaining": 463 }
```

## Errors

Errors use the same versioned envelope with an `error` object instead of `data`:

```json
{ "api_version": "v1", "schema_version": "1.0.0",
  "error": { "code": "insufficient_scope",
             "message": "This API key is missing the required scope 'jobs:write'.",
             "details": { "required_scope": "jobs:write", "scopes": ["jobs:read"] } } }
```

| HTTP | `code` | Meaning |
|------|--------|---------|
| 400 | `validation_error` | Missing/invalid request fields. |
| 401 | `invalid_api_key` | Missing or unrecognised key. |
| 401 | `key_revoked` | The key has been revoked. |
| 403 | `insufficient_scope` | Key lacks the required scope. |
| 403 | `forbidden` | Key's owner doesn't own the target project. |
| 404 | `project_not_found` / `job_not_found` / `report_not_ready` | Not found / not ready. |
| 409 | `scan_in_progress` | A scan is already running for that project. |
| 429 | `rate_limited` / `quota_exceeded` | Per-minute rate or monthly job quota hit. |
| 500 | `internal_error` / `database_error` / `auth_error` | Server-side failure. |

## Provisioning

Until the key-management UI ships, an operator provisions a key out of band:

1. Apply `crawl-rank-riot/migrations/2026-10-22_0001_v1_jobs_api.sql` and
   regenerate `database.types.ts`.
2. Mint a key with `generateApiKey()`
   (`crawl-rank-riot/src/services/api/v1/keys.ts`), insert a row into `api_keys`
   with the `key_prefix`, `key_hash`, `user_id`, `scopes`,
   `rate_limit_per_min` and optional `monthly_quota`, and hand the raw key to
   the integrator once.

---

## Notes & limits

- The crawler runs as a single process today, so the rate limiter is in-memory
  (per instance) and cancellation is in-process. A distributed store is future
  work if the crawler scales out.
- One scan runs per project at a time (`409 scan_in_progress`).
- `schema_version` is `1.0.0`; `deduction.penalty` is a raw weighted-model float.
